## 2026-10-13 이슈 수정 검토

위 표의 Storage 784MB와 하루 123MB·상시 790MB는 종목별 피처를 쓰던 시점의 기록이다. 현재 main은 피처를 이미 하루 한 파일로 저장한다. 날짜별 가격은 종목별이라 하루 약 25MB·상시 약 300MB로 추정되지만 게시 후 총량 실측은 필요하다.

실제 [차트 실행 38379035619](https://github.com/2026Graduation-Work/take_a_look/actions/runs/38379035619)은 10/13 기준 게시·retention·수급·종목 마스터 단계까지 성공했다. retention은 오래된 피처 기록 3,767행·Storage 객체 1,885개와 날짜별 입력 3개를 정리했다. 객체 수를 용량으로 환산하거나 새 총량으로 기록하지 않는다. 이 환경에는 Supabase 관리 조회 자격 증명이 없어 `budget_usage()`로 게시 후 총량을 측정하지 못했다.

`fix/open-issues-20261013`의 로컬 수정은 날짜별 가격을 `raw-prices-v3/<as_of>/batch.parquet`와 `batch.manifest.json`으로 묶는다. manifest의 파일 SHA-256과 종목별 원본 입력 해시를 검사하고, 기존 종목별 가격 파일 읽기도 유지한다. replay는 입력을 읽기만 하며 입력 파일을 다시 업로드하지 않는다. 오래된 달력과 DB 유니버스도 남은 게시 배치의 가장 오래된 기준일에 맞춰 정리한다. 보존 중인 DB 행이 참조하는 피처 객체는 삭제하지 않는다.

이 수정은 아직 운영에 적용되지 않았다. 승인된 반영 이후 `budget_usage()`와 경로별 용량을 측정하고, 최근 게시 배치 5개 보존 상태에서 Storage 600MB 이하인지 확인해야 #249·#286의 운영 완료 조건을 충족한다. 700MB 경고와 1GB 무료 한도는 그대로 유지한다.


승인된 반영에는 차트 워크플로의 `Measure retained chart storage budget` 단계가 포함된다. 기존 `budget_usage()` RPC를 읽어 실제 `storage_bytes`·`db_bytes`와 `retained_batches`를 로그에 남긴다. 600 MiB 초과는 경고로 남기며, 측정값과 보존 배치 수를 확인하기 전에는 추정치를 실측으로 바꾸지 않는다.

2026-10-14 08:51 KST [감시 실행 38486700270](https://github.com/2026Graduation-Work/take_a_look/actions/runs/38486700270)에서 DB 150MiB·Storage 353MiB·NewsAPI.ai 1,866회·마지막 차트 기준일 10/13·경고 없음·인증 Site URL 정상임을 확인했다. 이전 784MB 경고는 현 시점 총량과 다르다. 새 일일 가격 panel을 사용한 실행과 보존 배치 수는 다음 차트 실행의 실측 단계에서 확인한다.
