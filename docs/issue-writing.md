# 이슈 작성 안내

이슈에는 사용자 문제, 선택한 해결 방식과 이유, 완료 조건, 실제 검증 결과를 남깁니다. 처음 제안한 사람과 나중에 구현·검토하는 사람이 같은 맥락을 이해할 수 있게 작성합니다.

## 템플릿 선택과 작성 시점

| 상황 | 템플릿 | 접수할 때 | 조사·구현하면서 |
|---|---|---|---|
| 정해진 동작과 실제 동작이 다름 | [버그 보고](../.github/ISSUE_TEMPLATE/bug_report.md) | 1~3의 증상·재현 절차·기대 동작 | 1~4의 추가 맥락과 5~7의 원인·해결 결정·회귀 검증·결과 |
| 새 동작이 필요하거나 기존 동작을 개선함 | [기능 추가·고도화](../.github/ISSUE_TEMPLATE/feature_request.md) | 1의 사용자·불편과 2의 원하는 결과 | 구현 전 1~8의 근거·효과 측정·범위·선택 이유·완료 조건·검증·제약, 9의 결정·결과 |

1. 이슈 제목에 증상이나 달성할 결과를 적습니다. 예를 들어 `[버그] 뉴스 기준일이 지난 데이터가 오늘로 표시됨`처럼 작성합니다.
2. 처음에는 아는 내용만 적습니다. 측정 계획과 범위 확정은 담당자가 보완합니다. 모르는 내용은 `미확인`, 예상은 `가설`, 적용되지 않는 항목은 `해당 없음`과 이유를 적습니다.
3. 구현 전에 목표 동작과 완료 조건을 구체화합니다. 구현을 막는 미결 사항과 필요한 합의를 확인합니다. 작은 수정은 항목마다 한 문장으로 작성해도 됩니다.
4. 구현하면서 새로 확인한 사실과 결정 변경을 기록합니다. 검증 뒤 실제 결과를 추가합니다.

동작의 기준 자체가 정해지지 않았다면 기존 결함이라고 단정하지 말고 `합의 필요`로 표시합니다. 취약점은 공개 이슈 대신 [보안 제보 절차](../SECURITY.md)를 따릅니다. 첨부 자료에는 실제 계좌·보유 화면과 그 안의 종목·수치, 개인정보, 비밀키를 넣지 않습니다.

## 문제와 기대 효과 작성

- 대상 사용자가 어떤 상황에서 무엇을 하려다 막히는지 적습니다. 사용자 외에 운영자·개발자가 겪는 문제도 같은 방식으로 적습니다.
- 관찰·문의·인터뷰·로그·문헌을 근거로 연결합니다. 과거 조사라면 조사 시점과 현재에도 적용되는지 적습니다. 출발점으로 [초보 투자자 문제 점검](product/beginner-gap.md)을 참고할 수 있습니다.
- 왜 지금 필요한지 설명합니다. 영향받는 사용자, 반복 빈도, 잘못 판단할 위험, 우회 방법의 한계를 근거로 우선순위를 정합니다.
- 효과를 수치로 예상한다면 기준선·목표·측정 조건을 적습니다. 측정하지 않은 수치를 관측값처럼 적지 않습니다. 정량화가 어려우면 사용자가 수행할 과제와 성공 판단 방법을 적습니다.

## 동작과 검증 작성

완료 조건은 사용자가 보거나 시스템이 출력하는 결과로 작성합니다. `컴포넌트 구현`, `테스트 추가`는 작업이며 완료 조건을 대신하지 않습니다.

다음은 템플릿 작성법을 보여 주는 가상의 예시입니다. 현재 기능의 결함이나 실제 사용자 평가 결과를 뜻하지 않습니다.

| 항목 | 작성 예시 |
|---|---|
| 문제 | 초보 사용자가 데이터 기준일과 화면 조회일을 구분하지 못할 수 있다. 사용자 관찰로 확인할 가설이다. |
| 목표 동작 | 뉴스 집계일이 시장 공통 기준일과 다르면 뉴스 영역에서 집계일을 확인하고, 출처는 상세 하단 '데이터 출처·기준'에서 확인할 수 있다. |
| 완료 조건 F1 | 뉴스 집계일이 시장 공통 기준일보다 이른 테스트 데이터를 열면, 뉴스 영역에 실제 집계일을 표시하고 하단 '데이터 출처·기준'에 해당 출처를 표시한다. |
| 완료 조건 F2 | 집계 날짜가 없는 테스트 데이터를 열면 날짜 미확인 상태를 표시하고 조회일을 대신 넣지 않는다. |
| 동작 검증 | 기준일이 다른 고정 데이터와 날짜 없는 고정 데이터로 표시 문구를 확인한다. 실행 명령·환경·실제 출력·증거를 결과란에 남긴다. |
| 기대 효과 검증 | 사용성 평가에서 '이 정보는 언제 기준인가요?'를 묻고 답변 근거를 기록한다. 구현 전에는 미측정으로 두고, 평가 대상·성공 판단 기준·시점을 정한다. |

1. 정상 흐름을 `시작 상태·입력`, `행동·실행`, `기대 결과`로 나눠 적습니다.
2. 해당하는 결측·오래된 데이터·실패·권한 차이 사례를 추가합니다. 버그라면 원래 재현 사례와 유지돼야 할 정상 동작을 포함합니다.
3. 각 완료 조건 ID와 검증 방법을 연결합니다. [협업 규칙](CONTRIBUTING.md)의 영향 블록별 필수 검증도 실행합니다.
4. 실제 결과에는 명령 또는 수동 절차, 버전·환경·데이터 조건, 통과·실패와 증거를 적습니다. 미실행 항목은 이유를 적고 체크박스를 비워 둡니다.

기능이 명세대로 동작해도 사용자 불편이 줄었는지는 별도 확인이 필요합니다. 기대 효과를 아직 평가하지 못했다면 `효과 미확인`으로 표시하고 담당자·확인 시점·후속 이슈를 남깁니다. 구현 완료를 효과 입증으로 바꾸어 적지 않습니다.

## 선택 이유와 결정 변경 기록

선택한 방식이 사용자 문제를 해결하는 원리를 설명합니다. 다른 방식과 현재 상태를 유지하는 방안도 비교합니다. 비용, 무료 한도, 사용자의 이해, 데이터 정확성처럼 실제 선택에 영향을 준 조건을 적습니다. 대안이 없었다면 비교를 꾸며 내지 말고 그 이유를 적습니다.

앞의 가상 예시라면 '시장 바의 공통 기준일만 유지'와 '공통 기준일과 다른 뉴스 집계일을 뉴스 영역에 추가 표시'를 비교합니다. 뉴스 집계 시점의 혼동을 줄이기 위해 후자를 제안했다고 기록할 수 있습니다. 표시 공간이 늘어나는 단점도 남깁니다. 다른 데이터에도 같은 혼동이 확인될 때 [화면 규칙](../frontend/DESIGN.md)에 따라 날짜 안내를 재검토한다는 조건을 함께 남깁니다.

- 결정 표에 날짜, 결정 상태, 결정한 사람, 이유와 근거를 추가합니다. 제안을 합의 없이 `확정`으로 바꾸지 않습니다.
- 판단이 바뀌면 이전 결정과 당시 근거를 남기고 대체 결정을 연결합니다. 최신 목표 동작·완료 조건·검증 계획도 함께 맞춥니다.
- 문제가 같은데 해결 방법이 바뀌었다면 같은 이슈에서 이력을 이어 갑니다. 별도의 사용자 문제나 독립적인 변경이면 새 이슈를 열고 연결합니다.

## 프로젝트 문서와 PR 연결

이슈는 해당 변경의 의도와 결정 이력을 보존합니다. 현재 계약과 운영 방법은 [AGENTS.md의 작업별 정본](../AGENTS.md#작업별-정본)을 따릅니다. 정본의 설명이 바뀌면 관련 문서도 갱신하고 이슈에서 연결합니다. 기존 정본과 다른 계약을 이슈에서만 확정하지 않습니다.

- 관련 블록을 [협업 규칙의 블록 표](CONTRIBUTING.md#블록과-커밋)에 맞춰 적습니다. 여러 블록에 걸친 이슈는 블록별 PR이나 하위 이슈를 연결하고 선후 관계를 적습니다. PR당 한 블록 원칙은 유지합니다.
- 프로젝트 제약 중 변경에 해당하는 것만 설명합니다. 예를 들어 성향 정보가 종목 제외에 쓰이는지, 점수 계산이 결정론적인지, 데이터 출처·기준일이 드러나는지 확인합니다.
- 스키마·DB 계약 변경 합의와 운영 적용 확인은 기존 규칙을 따릅니다. 이슈의 완료 체크는 팀 합의나 운영 적용 승인을 대신하지 않습니다.
- [PR 템플릿](../.github/pull_request_template.md)의 관련 이슈에 연결합니다. '변경 사항'에는 선택 이유를 요약하고, '확인한 방법'에는 실제 실행 결과를 적습니다. 이슈에 이미 있는 설명은 연결해 중복을 줄입니다.
- 종료할 때 해결 PR, 실제 반영 버전·환경, 최종 동작을 확인할 문서, 미검증 사항과 후속 이슈를 기록합니다. 배포하지 않았다면 미배포로 적습니다.
