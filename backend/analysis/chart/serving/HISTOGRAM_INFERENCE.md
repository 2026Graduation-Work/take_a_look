## 1. 목표와 확정 범위

`backend/analysis/chart/serving/`에 서비스 실행에 필요한 코드·설정·모델·데이터를 모읍니다. 매일 실제 가격을 수집하고 H5/H20 모델로 추론한 뒤, walk-forward 과거 사례의 실현 수익률 히스토그램과 함께 Supabase에 누적 저장하고 화면에 표시합니다.

확정 사항:

- 실제 표본이 한 건이라도 있으면 히스토그램에 표시합니다.

완료 기준은 **기존 실제 자료로 히스토그램 생성 → 최신 실제 데이터 추론 → Supabase 적재 → 상세 화면 표시 → GitHub Actions 실행**까지 확인하는 것입니다.

- 복사 직후에는 수식과 동작을 보존하고, 이번에 합의한 표본 선택 방식 변경을 별도 단계로 적용합니다.

## 4. 과거 표본과 히스토그램 계산

### 과거 표본 생성

기존 walk-forward 예측과 종목별 가격을 연결해 다음 정보를 만듭니다.

```text
종목, 예측일, horizon, fold, 학습 종료일,
상방 점수, Sigma, 관측 완료일, 실현 수익률
```

수익률은 기존 거래정지 표시를 기준으로 다음 H개 실거래 행을 찾아 계산합니다.

```text
실현 수익률(%) =
    (H거래일 뒤 수정종가 / 예측일 수정종가 - 1) × 100
```

- H5/H20 표본을 분리합니다.
- 후속 가격이 없어 결과가 확정되지 않은 표본은 제외하고 사유별 건수를 남깁니다.
- 수익률 히스토그램 생성에 배리어 라벨 재계산이나 과거 하방 점수 복원을 요구하지 않습니다.
- 중복 키·잘못된 숫자·가격 연결 실패는 집계하거나 오류로 보고하며 조용히 덮어쓰지 않습니다.
- 기존 휴장일 문제를 정정하기 위한 전체 재처리·재학습은 수행하지 않습니다.
- 원본 예측 수, 사용 가능한 표본 수, 제외 사유를 pack 생성 보고서에 기록합니다.

### 현재 추론값과 비교하는 조건

| 항목 | 확정 규칙 |
|---|---|
| 기간 | 같은 H5 또는 H20 |
| 학습 정책 | pack에 지정된 같은 walk-forward 정책 |
| 종목 범위 | 해당 정책의 여러 종목 표본 |
| 상방 점수 | 현재 점수와 절대 차이 ≤ **0.01** |
| Sigma | 현재 Sigma와 차이 ≤ **현재 Sigma × 0.05** |
| 결합 | 모든 조건을 동시에 충족 |
| 경계 | 포함, 비교 전 반올림하지 않음 |
| Sigma 0 | 과거 Sigma도 0인 경우만 선택 |
| 관측 시점 | 예측일은 조회 기준일 이전, 결과는 기준일까지 확정 |
| 자동 확대 | 없음 |
| 최소 표본 수 | 없음 |

예를 들어 점수 `0.63`, Sigma `0.020`이면 점수 `0.620~0.640`, Sigma `0.019~0.021`인 과거 사례를 선택합니다.

### 분포 표시

- 선택된 표본으로 기본 12개의 동일 폭 수익률 구간을 만듭니다.
- 마지막 구간은 오른쪽 끝값을 포함합니다.
- 모든 값이 같거나 1건뿐이면 해당 값을 중심으로 한 개의 유효한 구간을 만들어 표시합니다.
- 막대 건수 합계는 선택된 표본 수와 정확히 같아야 합니다.
- 중앙 68% 범위는 같은 표본의 16·84백분위로 계산합니다.
- 0건은 `no_cases`, 1건 이상은 실제 분포를 표시합니다.
- 건수가 적다는 이유로 표시를 막거나 다른 표본으로 대체하지 않습니다.
- 표본 수·포함 종목 수·표본 기간·fold별 건수를 함께 제공합니다.

과거 표본은 horizon과 점수 기준으로 정렬해 로드하고, 점수 범위부터 좁힌 뒤 Sigma를 비교합니다. 종목마다 전체 과거 파일을 다시 읽지 않습니다.

6. pack이 지정한 builder로 피처를 계산하고 Supabase Storage에 저장합니다.
7. 같은 피처 입력으로 H5/H20 모델을 추론합니다.
8. 각 결과의 점수·Sigma로 과거 표본을 골라 히스토그램을 계산합니다.
9. 화면용 snapshot을 저장하고 H5/H20 배치를 한 번에 공개합니다.

수정주가가 바뀔 수 있으므로 단순히 마지막 날짜 이후 행만 붙이지 않습니다. 피처 계산에 쓰는 최근 구간을 다시 조회해 기존 값과 함께 갱신합니다.

### 저장 형태

| 자료 | 저장 위치·식별 |
|---|---|
| 실제 가격 | Supabase DB, 종목·거래일 기준 upsert |
| 가공 피처 | 비공개 Supabase Storage, 계산 버전·기준일·입력 해시별 Parquet |
| 피처 저장 정보 | DB에 Storage 경로·입력 해시·builder 버전 기록 |
| 추론·히스토그램·가격 표시 자료 | 날짜별 batch와 종목·H별 snapshot |
| 실행 상태 | batch 기록에 처리 건수·실패 사유·pack ID 기록 |

- 가격에는 OHLCV와 확보한 거래대금·수정계수 등 피처 재계산에 필요한 원천 필드를 저장합니다.
- 피처 업로드가 완료된 뒤 저장 완료 정보를 기록합니다.
- 전체 raw·피처를 브라우저에 전달하지 않고, 화면에 필요한 자료만 공개 snapshot에 포함합니다.
- `serving/data/`는 실행 작업 공간이며, 새 runner에서도 Supabase와 pack으로 필요한 상태를 복원합니다.
- 미래 라벨을 계산하지 않고 현재까지의 입력만으로 일일 피처를 만듭니다.
- 기존 모델과 실제 VWAP의 동등성 미검증은 기록하되 이번 실행을 차단하지 않습니다.

### 실패·재실행

- 같은 날짜·pack·입력·계산 버전은 같은 배치 식별자를 사용합니다.
- 동일 실행을 반복해도 가격·피처·추론 결과가 중복 누적되지 않게 합니다.
- 종목별 가격 부족은 해당 종목의 `unavailable` 상태로 기록합니다.
- 전체 수집 실패·모델 로드 실패·필수 저장 실패 시 새 배치를 공개하지 않습니다.
- 공개 전 실패하면 이전 공개 배치를 유지합니다.
- 입력 정정이나 새 pack으로 같은 날짜를 재실행하면 새 배치를 만들고 공개 완료 시 교체합니다.

## 6. DB 계약·화면·GitHub Actions

### DB와 공개 계약

현재 DB에는 기존 사례 정책 ID와 응답 계약 이름을 제한하는 조건이 있으므로, JSON 필드 추가만으로 끝내지 않습니다.

- 기존 배치·snapshot·공개 RPC 구조를 활용하는 추가 migration을 작성합니다.
- 새 히스토그램 정책과 `chart_signal_detail_v2`를 지원합니다.
- 새 계약에는 실제 추론, 가격 이력, histogram, 비교 조건, 출처·기준일·pack ID를 포함합니다.
- 기존 같은 종목 상하방 충족 사례와 새 여러 종목 수익률 분포의 의미를 구분합니다.
- Python 응답 검사와 프론트 타입을 함께 변경합니다.
- freeze된 `schema/`는 수정하지 않고 serving 전용 계약을 사용합니다.
- 가격·피처 기록과 Storage는 실행 계정이 쓰고, 브라우저는 공개 snapshot만 읽습니다.

### 상세 화면

- 기존 `ReturnHistogram`의 그리기 구현을 사용합니다.
- H5/H20 전환 시 추론 결과·가격 기준·분포를 함께 전환합니다.
- 표본 수와 포함 종목 수, 비교 점수·Sigma 범위, 과거 기간을 표시합니다.
- “같은 종목의 과거” 대신 “비슷한 신호·변동성 구간의 과거 사례”로 설명합니다.
- 중앙 범위 문구는 “과거 표본의 중앙 68% 범위”로 표시합니다.
- 0건·1건·조회 실패·오래된 기준일을 각각 표시합니다.
- 실제 데이터 조회 실패를 mock 데이터로 대체하지 않습니다.
- 연구 데모 상태와 실제 데이터 기준일을 표시합니다.
- 기존 구계약 데이터가 남아 있으면 해당 화면을 유지하되, 새 분포를 만들어 채우지 않습니다.

### GitHub Actions

- 평일 **18:30 KST** 예약과 수동 실행을 제공합니다.
- workflow는 serving 코드·requirements·pack만으로 실행합니다.
- Supabase 및 필요한 KRX 인증 정보는 Actions secrets로 전달합니다.
- 예약·수동 실행은 concurrency 설정으로 중복 실행을 막습니다.
- 일시적인 네트워크 오류는 제한된 횟수로 재시도합니다.
- 휴장일에는 새로운 당일 배치를 만들지 않습니다.
- 과거 날짜 수동 실행은 저장된 해당 날짜의 종목 목록과 입력을 사용하며, 없으면 명확한 사유로 종료합니다.
- 실행 로그에는 기준일·pack·처리 건수·실패 단계·공개 batch ID를 남깁니다.

## 7. 구현 순서와 검증 기준

### 구현 순서

1. serving 내부 코드와 데이터 경로 정리.
2. pack 계약·생성·로드 구현.
3. 기존 walk-forward 자료로 실제 H5/H20 과거 표본과 히스토그램 생성.
4. Supabase 가격·피처 저장과 최신 수집·추론 연결.
5. 새 snapshot 계약·DB migration·공개 흐름 연결.
6. 종목 상세 화면 연결.
7. GitHub Actions 수동 실행 및 예약 설정.
8. pack 교체·재실행·실패 복구 확인.

파일 이동·복사 정리와 계산 로직 변경은 구분해 커밋합니다. 현재 작업 중인 다른 변경을 덮어쓰지 않고 새 브랜치에서 작업합니다.

### 필수 검증

- **독립성:** 연구 폴더 없이 serving만 복사한 환경에서 pack 생성과 CLI 실행.
- **계산 보존:** 기존 계산과 복사한 구현의 동일 입력 결과 비교.
- **실제 자료:** 현재 H5/H20 모델과 walk-forward 예측으로 표본 수·제외 사유·히스토그램 생성 결과 확보.
- **표본 선택:** 점수 ±0.01, Sigma ±5%, 경계 포함, Sigma 0, 미래 관측 제외.
- **히스토그램:** 0건·1건·동일 수익률·음수 수익률·마지막 구간 포함·건수 합계.
- **모델 호환:** 피처 순서·누락·class 순서·파일 해시·H5/H20 혼합 검사.
- **저장:** 중복 재실행, 피처 업로드 실패, snapshot 일부 업로드 실패, 배치 교체.
- **화면:** 실제 데이터 표시, H5/H20 전환, 작은 표본, 실패 상태, 키보드 접근성.
- **자동화:** 깨끗한 Actions runner에서 실제 수집부터 Supabase 공개까지 성공.
- **교체:** 활성 pack 설정 변경으로 새 모델 사용, 이전 pack으로 복귀 가능.
- chart lint·관련 테스트·프론트 빌드를 통과하고 결과를 문서에 기록합니다.

코드 구현, 실제 DB 적용, 첫 실제 배치 공개, 예약 실행 확인은 각각 구분해 완료 여부를 기록합니다.
