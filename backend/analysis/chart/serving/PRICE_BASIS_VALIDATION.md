# 수정 가격 기준 검증 기록

기준일 2026-11-24. 범위는 서빙 수집·종목 마스터와 관련 문서다. 운영 데이터 쓰기, 삭제, 보존 기간 변경은 수행하지 않았다.

## 회귀 증거

`test_corporate_action_rebases_saved_history_and_chart_prices`는 400거래일의 합성 가격과 마지막 날 5대 1 분할을 사용한다. 저장 계수는 1, 새 구간의 과거 계수는 0.2, 분할 당일은 1이다. `collect`가 저장한 수정계수·수익률의 연속성, 원주가·거래량·거래대금 보존, DB로 전달한 전 이력의 수정 기준을 확인한다.

테스트를 먼저 추가한 `ddaa776`에서 다음 값 차이로 실패했다.

```text
E   Series values are different (56.75 %)
E   At positional index 0, first diff: 1.0 != 0.2
1 failed, 1 warning in 0.84s
```

보정 구현 후 같은 테스트가 통과했다.

```text
1 passed, 1 warning in 0.81s
```

chart 디렉터리에서 다음 명령으로 재현한다. 수정 전 실패는 `ddaa776`, 수정 후 통과는 현재 PR의 구현 커밋을 사용한다.

```bash
pytest serving/tests/test_daily_corrected_inputs.py::test_corporate_action_rebases_saved_history_and_chart_prices -q
ruff check .
pytest serving/tests
```

1차 구현의 서빙 테스트는 `107 passed, 7 warnings in 12.76s`였다. chart의 `ruff check .`도 통과했다. 경고는 기존 `exchange_calendars`의 NumPy timedelta 사용에서 발생했다. 분할·병합·2% 권리락, 반복 수집, 부분 DB 실패 후 재시도, 비일정 비율의 종목별 제외, 정상 분할과 계산 구간 밖 경계를 검증했다.

## 독립 리뷰의 추가 반례

- 원종가가 1,002원인 두 날짜와 4,000원인 날짜에 0.2 계수를 적용하고 원 단위로 반올림하면, 관측 비율의 중앙값은 약 0.1996이다. 실제 공통 비율 0.2가 모든 날짜의 허용오차를 만족해도 중앙값만 검사하면 거부했다. 날짜별 허용 구간의 교집합을 구하고 그 안으로 중앙값을 제한한다.
- 전체 DB upsert가 첫 500행 뒤 실패하고 다음 공급자가 이전 계수를 반환하면, 새 비율이 1이라는 이유로 앞부분의 DB 재시도를 생략했다. 이전 가격과 `price_rebase_pending` 속성을 먼저 Storage에 남겨, 다음 실행의 공급자 기준과 관계없이 전체 upsert를 완료한다. 성공한 최종 이력에서는 이 속성을 지운다.
- 새 입력이 저장 날짜 전체를 덮고 보존할 앞부분이 없으면, 겹치는 거래량이 모두 0이어도 새 이력으로 안전하게 대체할 수 있다. 앞부분이 남는 장기 거래정지 종목은 비교할 거래가 없어 미확인 상태가 이어질 수 있으므로 운영 확인이 필요하다.

추가 반례 테스트는 수정 전에 `3 failed, 33 deselected in 0.77s`를 기록했다. 수정 후 서빙 전체 결과는 다음과 같다. 독립 리뷰에서도 같은 테스트 전체가 통과했고, Parquet 왕복과 실제 500행 전송 경로에서 DB·Storage 불일치가 0개임을 확인했다.

```text
112 passed, 7 warnings in 13.31s
```

최종 `ruff check .`, `git diff --check`, 문서 링크·색인 검사도 통과했다. 최종 경고 7개는 기존 `exchange_calendars`의 NumPy timedelta 사용에서 발생했다.

## 쓰기 요청량과 무료 한도

`scheduled_sessions`로 2016-01-01부터 2026-11-23까지 거래일을 만들고 `SupabaseStore.upsert_prices`의 전송 함수만 메모리 기록으로 교체했다. 가짜 코드 `000000`과 일정한 가짜 가격을 사용했다. 요청별 최대 500행, 날짜별 중복 없음, 전송 행 수와 입력 행 수 일치를 단언했다. 실제 네트워크 요청은 없었다.

| 합성 입력 | 행 수 | upsert 요청 수 | 직렬화 JSON 바이트 |
|---|---:|---:|---:|
| 전체 이력 | 2,670 | 6 | 696,870 |
| 최근 240달력일 | 161 | 1 | 42,021 |

표의 요청 수는 DB upsert만 세며 `ceil(행 수 / 500)`이다. 보정 시작 시 기존 Storage 이력에 미완료 속성을 저장하는 요청 1회와, DB 완료 후 새 이력을 저장하는 요청 1회가 별도로 필요하다. 이미 미완료 속성이 있으면 시작 기록을 반복하지 않는다. JSON 크기는 가짜 가격의 직렬화 결과이며 실제 DB·인덱스 증가량이나 트래픽 잔량이 아니다. 보정한 종목은 DB에 없던 과거 날짜도 추가할 수 있다.

11월 24일 09:08 KST의 기존 게시 로그는 DB 165,981,331바이트와 Storage 217,858,323바이트를 기록했다. 각각 약 158MiB와 208MiB로, [무료 운영 목표](../../../../docs/ops/free-tier-budget.md)의 DB 300MiB와 Storage 600MiB보다 작다. [기존 게시 작업의 용량 측정](https://github.com/2026Graduation-Work/take_a_look/actions/runs/45272346608/job/138035212182#step:13:1)

## 운영 확인과 복구 계획

현재 세션에 서비스 키가 없어 운영 `chart_prices`와 `raw-history-v3`의 영향 종목 목록을 직접 조회하지 못했다. 공개 anon 키는 `chart_prices`를 읽을 수 없다. 기존 운영 로그만 확인했다. 이 기록으로 전 종목 백필의 무료 한도 충족을 단정하지 않는다.

1. 읽기 전용으로 종목별 수정계수 경계·수정종가와 원종가 수익률·전체 날짜 범위를 조회한다. 공급자의 최신 구간과 Storage 겹침 비율도 비교해 후보를 확인한다.
2. 영향 종목 목록, 전체 upsert 행 수, DB에 없는 신규 날짜 수, 예상 요청 수를 산출한다. 최신 DB·Storage 사용량과 트래픽 잔량을 다시 확인한다.
3. 목록과 무료 한도 내 처리 계획을 팀에 제시하고 운영 복구 여부를 확인받는다. 전체 재조회는 일일 수집에 추가하지 않는다.
4. 승인된 종목만 검증된 공급자 이력으로 DB를 먼저 upsert하고 Storage를 맞춘다. 경계 제거와 두 저장소의 공통 날짜 일치 후 종목 마스터를 다시 계산한다. 행 삭제와 보존 변경은 하지 않는다.

이미 두 저장소에 같은 경계가 있고 새 겹침 비율이 1이면 이번 예방 로직으로 자동 복구하지 않는다. 종목 마스터의 의심 경계 검사는 가격만으로 확정할 수 없는 휴리스틱이다. 작은 경계가 시장 수익률에 상쇄되면 놓칠 수 있다. 정상 배당락일의 큰 시장 움직임도 변동성 미확인으로 처리할 수 있다.

`local_preview --code 005930 --as-of 2026-10-06 --compute-only`는 로컬 운영 pack과 출처 manifest가 없어 완료하지 못했다. 연구 입력으로 대체하지 않았다. 이번 변경의 수집·저장·종목 마스터 경로는 모의 저장소 테스트로 검증한다.
